# API Conventions

STATUS: **DRAFT**
Version: **v1**

These conventions apply to every endpoint, schema, and WebSocket event in the Warangal Trading Ring API. All agents must adhere to them without exception.

---

## 1. Timestamps

- All timestamps are **UTC**.
- All timestamps use **ISO-8601** with explicit `Z` suffix.
- Example: `"2026-01-01T10:30:00.000Z"`
- Millisecond precision is preferred for trading events.
- Clients must not assume local timezone. The server is the time authority.
- `created_at` and `updated_at` are always present on domain objects that change over time.

---

## 2. Financial Values (CRITICAL)

Binary floating-point MUST NOT be used for money, prices, or P&L at the API boundary.

All financial values are transmitted as **decimal strings**.

```json
{ "price": "24510.25" }       ← CORRECT
{ "price": 24510.25 }         ← FORBIDDEN
{ "price": 24510.2500001 }    ← FORBIDDEN
```

Applies to:
- prices
- balances (available cash, reserved cash, portfolio value)
- P&L (realized, unrealized, daily, total)
- average prices
- execution prices
- percentage returns (expressed as strings, not floats)

**Rounding responsibility:**
- The Order Execution Service and backend are responsible for rounding precision in calculations.
- The API preserves whatever decimal precision the engine produces; it does not silently truncate.
- The frontend is responsible only for *display rounding* (e.g., showing 2 decimal places). It must never round for calculation purposes.
- Exact PostgreSQL numeric precision is an Agent 4 decision. The API contract only requires that the string representation preserves the authoritative value without floating-point loss.

**Quantities** (number of shares/units):
- Transmitted as integers or decimal strings depending on whether fractional quantities are supported.
- Initial assumption: quantities are **positive integers** (whole units only).
- If fractional quantities become a requirement in a future version, this is a breaking change requiring schema updates.

**Percentages** (e.g., return %):
- Transmitted as decimal strings representing the percentage value directly.
- Example: `"5.42"` means 5.42%, not 0.0542.

## 3. Identifiers

| ID Type | Format | Generated By | Public? | Notes |
|---------|--------|--------------|---------|-------|
| `user_id` | `usr_<ulid>` | Backend | Yes | Stable, opaque |
| `order_id` | `ord_<ulid>` | Backend | Yes | Stable, immutable after creation |
| `client_order_id` | Up to 64 chars, `[a-zA-Z0-9_-]` | Client | Yes | Idempotency anchor |
| `execution_id` | `exe_<ulid>` | Backend/Engine | Yes | Stable, immutable |
| `event_id` | `evt_<ulid>` | Backend | Yes | For WebSocket dedup |
| `request_id` | `req_<ulid>` or client-provided | Client or Backend | Yes | Logging correlation |
| `Idempotency-Key` | Up to 128 chars, `[a-zA-Z0-9_-]` | Client | Header only | For safe retries |

**ULID format:** `01ARZ3NDEKTSV4RRFFQ69G5FAV` (26 uppercase alphanum, time-sortable). Backend may use UUID v4 instead — the format within the prefix is an Agent 2 decision, but the prefix convention and public stability guarantee are fixed by this contract.

**Rules:**
- Internal database primary keys (integer sequences, raw UUIDs) must NOT be exposed in the public API.
- IDs are opaque to the client. Clients must not parse or construct IDs.
- `client_order_id` is the one ID the client generates. See `orders.md` for rules.
- IDs are stable: once assigned, they never change for the lifetime of the resource.

---

## 4. Request ID

Every request carries a `X-Request-ID` header.

**Client-provided:**
```
X-Request-ID: req_01ABC123...
```
- Optional. If the client provides it, the backend uses it for logging.
- Must match `[a-zA-Z0-9_-]{8,128}`.
- If invalid, the backend generates its own and ignores the client-provided value.

**Server-generated:**
- If the client does not provide `X-Request-ID`, the backend generates one.

**Response:**
- Every response includes `X-Request-ID` in the header echoing the final request ID used.
- Every response body includes `"request_id"` in the envelope.

**Purpose:** Logging correlation. If a user reports an error, they can provide this ID to trace the request through all backend systems.

---

## 5. HTTP Methods

| Method | Use |
|--------|-----|
| `GET` | Read state. Never mutates. Safe to retry. |
| `POST` | Create or submit a command. Not idempotent unless `Idempotency-Key` is used. |
| `PATCH` | Partial update (not widely used in this API; prefer named action endpoints). |
| `DELETE` | Not used in this API. Cancellation is `POST /orders/{id}/cancel`. |

---

## 6. Content Type

All requests with a body: `Content-Type: application/json`
All responses: `Content-Type: application/json`

No XML, no form encoding, no multipart.

---

## 7. Pagination

Two strategies are used. The choice per endpoint is documented in that endpoint's file and is fixed — do not mix strategies on the same endpoint.

### Cursor-based (for open-ended or growing collections)

```json
{
  "data": [...],
  "next_cursor": "cursor_opaque_string_or_null",
  "request_id": "req_123"
}
```

- `next_cursor` is `null` when there are no more pages.
- Client passes `?cursor=<value>` on next request.
- Default page size: **50**
- Maximum page size: **200** (enforced server-side; requests above max return 200 items)
- Ordering is defined per endpoint.
- Cursors are opaque. Clients must not parse or construct them.
- **Used for:** orders (unbounded, grows with trading activity)

### Offset-based (for bounded, ranked collections)

```json
{
  "data": [...],
  "total": 42,
  "offset": 0,
  "limit": 50,
  "request_id": "req_123"
}
```

- **Used for:** leaderboard — participants are a bounded set (250–500), the collection is ranked by position, and offset pagination lets the UI jump directly to a rank range (e.g., "show ranks 51–100") without cursor traversal. This justifies offset over cursor for this specific endpoint.
- Cursor pagination is preferred for all other collections.

---

## 8. Standard Response Envelope

### Single object

```json
{
  "data": { ... },
  "request_id": "req_123"
}
```

### Collection (cursor)

```json
{
  "data": [ ... ],
  "next_cursor": null,
  "request_id": "req_123"
}
```

### Error

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable description.",
    "details": {}
  },
  "request_id": "req_123"
}
```

There is no mixed `data` + `error` in the same response. A response either succeeds or fails.

---

## 9. Nullability vs Optionality

- A field marked **optional** in a request may be omitted entirely by the client.
- A field marked **nullable** in a response may be present with a `null` value.
- A field that is neither: always present, never null.
- These distinctions are explicit in every schema in `contracts/schemas/`.

---

## 10. JSON Conventions

- Property names: `snake_case`
- Enum values: `UPPER_SNAKE_CASE`
- Booleans: `true` / `false` (not strings)
- Empty collections: `[]` not `null`
- Unknown enum values: clients must tolerate unknown values gracefully (forward-compatibility)

---

## 11. API Versioning Rules

- All endpoints: `/api/v1/...`
- Breaking changes → new version `/api/v2/...`
- v1 endpoints remain operational for a defined deprecation window (Agent 2 configuration decision — does not affect public contract)
- `Accept-Version` header is NOT used. Version is in the path only.

---

## 12. Authentication Headers

Authenticated requests carry a bearer token:

```
Authorization: Bearer <token>
```

The token format (JWT, opaque, etc.) is defined in `auth.md`.

---

## 13. Sensitive Information Rules

- Passwords, secrets, tokens must never appear in URLs (query params or path).
- Tokens must be in `Authorization` header only.
- Participant IDs in path parameters are acceptable for owned resources (e.g., the authenticated user's own data).
- A participant must never be able to access another participant's private data by substituting a path parameter.

---

## 14. V1 Execution Model Convention

This section states the fundamental execution model that ALL contracts in this package are built on. Any terminology or behavior that contradicts it is an error.

**Warangal Trading Ring V1 is not an exchange.**

| Property | V1 Behavior |
|----------|-------------|
| Order types | MARKET only |
| Execution | Immediate, against authoritative market price |
| Order book | Does not exist |
| Participant-to-participant matching | Does not exist |
| Counterparty | Does not exist |
| Partial fills | Not expected in normal operation |
| Matching engine | Does not exist |
| Execution component | Order Execution Service (terminology used across all contracts) |

**Normal order flow:**
```
POST /orders → PENDING → ACCEPTED → FILLED
```

Every valid MARKET order that passes all validation checks is expected to be completely `FILLED` in a single execution against the authoritative market price.

**REST is the authoritative state source.** WebSocket is the notification channel. After any disruption, REST re-fetch restores truth.
